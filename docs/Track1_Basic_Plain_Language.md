# PRD 4.2 Basic 白话版（会议速读）

对应 [PRD 4.2](Track1_Data_Assessment_and_PRD.md)。这份文档解释原需求，不增加新功能。**Basic 是希望最终演示满足的要求，不代表当前原型已经完成。**

## 一句话看完整流程

用户确定**一块地**，填入**一个住宅建设方案**；系统用能查证的分区规则和地图数据做**初步筛查**，给出有限范围的等级、证据、没查到的事项，以及下一步该找谁确认。

## 先让输入和结果对得上（B1–B3）

- **B1 找地块：** 可以在地图上点，或输入地块编号（parcel ID）。如果搜地址出现多块地，让用户选定其中一块；找不到或不在匹兹堡市内，就解释原因。**没确定唯一地块，不能出报告。**
- **B2 填建设方案：** 至少支持一个已经核对过规则的方案，例如“多户住宅、12 套”。报告上要同时写地块编号和方案。用户改了方案，旧结论要作废并重算。
- **B3 地图和报告同步：** 地图高亮、地块信息、方案、报告必须指向同一块地。地块边界、面积、市界状态要能追到数据来源；查不到的地址或面积写“未知”。

## 查什么，怎样给等级（B4–B6）

- **B4 分区规则（zoning）：** 查这块地碰到哪些分区，再看该住宅方案在这些分区里的用途分类，并附法规链接。只有**人工核对过的“分区＋方案”组合**才给分类。若跨多个分区、附加限制（overlay）或建筑尺寸规则还没查，就明说。这里的结果不是建造许可。
- **B5 环境图层：** Basic 至少查一层“坡度达到 25% 的陡坡”地图数据。说明地块是否与它重叠，给出核验过的重叠面积或比例和数据日期。**地图重叠只表示需要进一步核查**，不能直接断言建筑会建在坡上或审批一定受阻。
- **B6 Development Ease 等级：** 先用**绿／黄／红**表示已核验的分区和场地条件，关键证据缺失时用**灰色：暂不能判断**。展示是哪条规则、哪份法规或地图数据导致这个结果，以及哪些因素没查。规则应固定、可复核；AI 不能自行决定等级。这里**不评土地能否取得或项目赚不赚钱，也不报获批概率**。现阶段不需要硬凑百分制。

## 报告怎样让人放心使用（B7–B10、B12）

- **B7 障碍与下一步：** 最多列 3 个最该先处理的障碍。每个写清“发现了什么 → 为什么相关 → 找谁/查什么 → 证据在哪”。没查到的内容另列“未知”，不能当作没风险。
- **B8 AI 文字：** AI 只能把已经查证的事实讲得更易读，不能补造法规或改等级。AI 不工作时，系统也要用固定模板出可读报告。
- **B9 来源和日期：** 关键结论旁边给来源、数据日期或获取日期、适用范围。第一页就提示“早期初筛，需人工复核”；正在讨论但尚未生效的政策要与现行规则分开。
- **B10 四类用户共用一份报告：** 规划师、开发商、住房公益组织、政策分析师不必先选角色。同一块地、同一方案的事实和等级相同；今后可以按关注点调整信息顺序。暂时没有角色视图，也要让四类用户都看得到证据和未知项。
- **B12 财务边界：** 报告第一页要明确写**本等级不包含财务可行性**。下一步要找本地租金/售价可比数据，估土地取得、建设、融资等成本。县评估值或一次成交价不能直接当作完整的市场比较或财务测算；绿色也不等于“肯定能赚钱”。

## 怎样证明不是只会播放 Mock（B11）

- **B11 可重复演示：** 选**一块真实地块＋一个住宅方案**，人工核对关键事实和规则；任何队友从网页输入，都能重复得到相同且有来源的结果。README 要讲清数据来自哪里、AI 做了什么、没覆盖什么。
- **当前原型与验收的区别：** 现有合成地块 A/B 和模拟洪水层可以说明交互，但它们**不能替代** B11 的真实地块验证；模拟洪水也**不能替代** B5 要求的 25% 陡坡图层。真实数据缺失时应显示灰色或未知，不能把 Mock 结论当成真实结论。

## 开会时可用的三个检查问题

1. 我们选的真实地块和住宅方案是什么？地块 ID、边界、分区规则、陡坡结果分别由谁核对？
2. 每个绿／黄／红结论旁边，能否直接看到依据？依据缺失时是否自动变灰？
3. 队友从空白页面重新输入一次，能否得到同一份带来源、日期、未知项和财务提示的报告？

**术语速查：** parcel ID＝地块的唯一编号；zoning＝土地用途分区规则；overlay＝叠加在基础分区上的额外限制；图层相交＝两张地图上的区域重叠；scenario＝用户拟建的住宅类型和规模；Mock＝演示交互的模拟数据。
